# H3 統合プロンプトの構築手順（job 3546 方式）

## ⛔ 検証で確定した前提（2026-08-22）— これを外すと何を書いても効かない

**セットアップは正常。品質が出なかった原因はプロンプトと演出設計だった。** 対照実験で確定:

| 実験 | 構成 | 結果 |
|---|---|---|
| job 3591 | 参考001をFL2VAで原文実行 / 1344×768 / 25step | **高品質**。文字・同一性・Z順すべて成立 |
| job 3592 | C18内容をRef2VA / **参照3枚** / **3,985字** | **高品質**。参照キャラの同一性も維持 |
| 従来のC18-19 | Ref2VA / **参照9枚** / **10,000〜20,000字** | 低品質。要素が消える |

差は**参照枚数とプロンプト長**。以下を守ること。

1. **状態の描写に文字数を使わない。** ルール・法則・技法語彙になら使ってよい
   (`detailed_description` の公式目標は **350〜500語**)
2. **1ショット = 1アクション弧 + 1カメラ運動**。4つ積まない
3. **カットは新情報(被写体/空間/状態/視点/時間)を導入するときだけ。**
   同じ人物の同じ場所で寄りを変えるのは**カットではなく push in**。
   誤用したカットは統合・無視される(= 「指定した人物が出ない」の正体)
4. **参照は絞る。** 9枚は視覚トークンがテキストと競合する。3枚で成立を確認済み
5. **参照には必ず役割を宣言する**(`source → contribution → target → boundaries`)。
   役割未宣言の参照は「使えそうな部分」を勝手に採られる = 属性混線の機序
6. **参照ボードの枠・文字・パネル・寸法図・設定資料レイアウトは出力しないと明記する**
7. **禁止は散文でなく正しいフィールドに肯定形で書く**(`non_diegetic_music: N/A` は効き、
   散文の "No background music." は落ちた)
8. **品質語(`cinematic` `4k` `masterpiece`)は書かない。** 拡散画像の悪癖。
   スタイルは Shot 1 冒頭のラベルに集約し、本文に散らさない
9. **回転・振り向きは動詞で書かない。** 終端状態を書く / 部位(腰・肩・頭)を列挙する /
   **既に反転した状態でカットする**のが最も確実
10. **1リトライ1変数。** 複数同時に変えると何が効いたか分からない

出典と詳細: `docs/prompt-refs/README.md`(参考プロンプト7件) と
`docs/h3-adherence-field-guide.md`(公式/コミュニティ/検証済みの知見)

## ⛔ 実尺厳守ルール（2026-08-22 ユーザー決定・厳守）

H3の最小生成尺は124f(5.2秒)だが、本プロジェクトのカットは88%がそれより短い
(中央値104f)。**プロンプトはカットの実尺で書く**。生成尺で書くと5.2秒分の芝居の
頭だけが使われ、モデルが組んだ着地が毎回捨てられる(「盛り上がらない」の構造的原因)。

- 書き方: カットが55fなら「**最初の2.3秒で全てが起こり、残りは余韻(残心/静止/減衰)**」と
  時間ブロックを実尺で割る。余韻部分は次カットへの糊代として単純な持続を書く
- 細かい打点合わせは**時間リマップ**(⏱)が担当する。プロンプトで打点は書かない
- 複数カット統合生成(Sequences)は例外: 合計実尺で書く(C18-19=221f≒9.2秒)

ユーザー評価: 「情報密度やテンポとしてはとても良好」(2026-08-21, W1_c18_integrated = job 3546)。
以後この手順を標準とする。実物のプロンプトは asset 2854 の gen_params_json に残っている。

## 参照フロー（プロンプトを書く前に必ず引くもの）

0. **キャスト名簿 `backend/data/bible/0.json`** ← ★2026-08-22 追加。忘れて事故った工程。
   キャラと **武器** の正典がここにある。`cast[].outfits` に `mg` / `mg_tv` / `school` に加えて
   **`weapon`** があり、英文記述と専用の参照画像IDが入っている。
   自分の記憶や想像で武器を書かない。実例:

   | key | weapon refs | 正典 |
   |---|---|---|
   | mami | 2788 | 白木銃床に銀の百合紋章、黒レシーバーに白唐草象嵌、銀銃身、真鍮撃鉄のフリントロック |
   | kyoko | 2782 | 金の柄+赤金の葉形穂先の槍。**柄が鎖で繋がれた節に分離**して鎖鞭になる(=多節棍は正式設定) |
   | sayaka | 2781 | 直刃片刃カトラス、黒柄に淡青の帯、平たい金の護拳 |
   | nagisa | 2783 | ファゴット型の角笛、橙紫青黄の分節、黄の花形キー |
   | madoka | 2780 | 淡褐色の枝に薔薇の蕾、握りに桃色の菱形宝石、桃色の光の矢 |
   | homura | 2785 | 砂時計の盾(中で砂と球が動く) |

   事故の記録: マミの銃を「クリーム色のリボン」と創作し、杏子の多節棍を自分の発明だと思って
   1回しか説明しなかった。どちらも名簿に正典がある。「再現度が低い」の主因はこれ。

1. **ピンの attrs_json**(該当カットの開始ピン) — ユーザーの意図・歌詞・指定アセット・promptDraft。
   これが最優先の入力。私の解釈で書かない。
2. **audio_drums**(該当カット区間の打点) — スネア/キック/シンバルの実測秒。
   カット区間は `t0 = 開始フレーム/24` から `+124/24` まで。
3. **audio_structure** — 区間の性格(サビ/メロ/…)。サビなら密度を最大に。
4. **LOOK**(共通撮影基盤) + **COMMON**(パレット4色 / STYLE融合1行 / Z順 / 末尾0.7秒静止)。
5. **キャラ定義は既存の規定文(parts.json 相当)を再利用** — 同一性に効くため文言を揺らさない。

## 打点 → 映像の割り当て

| 音 | 役割 | 書き方 |
|---|---|---|
| **スネア** | ハードカット | `[Shot N] At MM:SS.mmm,` に**そのまま**置く(8〜9ショット) |
| **キック** | 身体の衝撃 | 各ショットの窓に入る打点を `At MM:SS.mmm she 〜` で個別描写(踏込/着地/圧縮…) |
| **シンバル** | 光と粒子 | 同上。カメラは動かさず光だけで応答(火花/花びら/リムの明滅…) |

窓割り: スネアで区切った各ショット区間に、その中のキック/シンバルを配る
(builderは `windows.json` / `windows18.json` を生成した節を参照)。

## 構成要素

- **トランジションは技法名でなく実在の物体**: ケープ/羽根/槍先の裂け/1フレーム白飛び/花びら/
  グリッチ(同一瞬間の3回ホールド+色チャンネルずれ)/水ワイプ/影ワイプ/翼/帽子のつば
- **3D的カメラ**: 面(近/中/遠)を名指しし「近い柱は速くボケ、遠い柱はほぼ静止」と速度差を明記
- **緩急**: anticipation → 1フレームで解放 → overshoot → follow-through を全編に宣言
- **終わり**: 感情の着地(C19はまどかの表情のクローズアップ)+最後0.7秒完全静止

## 語数

- キャラ定義: 規定文字数を守る(同一性)
- それ以外: **1200語級でよい**。公式の350-500語は様式の参考であって上限ではない(ユーザー指示)

## 実測で分かっている限界

- この密度では**カットの時刻精度は出ない**(指定点一致が偶然と同水準)。
  時刻を正確に打ちたいカットは Y3L 方式(ショットを簡潔に、各点を深く)か編集で。
  熱量と精度は現状トレードオフ。

## T1下見プリセット(2026-08-22 v2)

`params["quality"]="t1"` の1フラグで最速構成に展開される(job_runner._generate_video_i2v)。

| | 通常(本番) | T1下見 v2 |
|---|---|---|
| 解像度 | 1344×768 | **960×544** (Ref2V Turboの学習解像度544p) |
| steps | 25 | 4 (Turbo LoRA蒸留) |
| LoRA | なし | **ref2v_turbo_4step_v0.1** (Ref2VA専用蒸留, 2026-08-13) |
| easycache | off | on |
| 実測(124f) | ≈31分 | **171秒 (≈11倍速)** — v1(640×368,fl2v流用)は57〜75秒だったが規定外 |

v1の反省(ユーザー指摘 2026-08-22): ①FL2V用LoRAをRef2VAに流用していた
②640×368は学習ドメイン(544p)も公式規定(短辺768)も割っていた。
LoRAはモード別に正しい方を使う: Ref2VA→`minimax_h3_ref2v_turbo_4step_v0.1_comfyui_bf16`、
FL2VA→`minimax_h3_fl2v_turbo_4step_v1.1_768p_comfyui_bf16`(768p学習)。
配布元: [lightx2v/Minimax-h3-Turbo](https://huggingface.co/lightx2v/Minimax-h3-Turbo)。
**LoRAは更新が速い(v0.1→v1.1が2週間)ので、ベンチ前にHFの一覧を必ず再確認する。**

用途は**プロンプトと構成の検証**。構図・配置・キャラ判別は読めるが質感は崩れる。
⚠ Turbo LoRAは重みが変わるため**同じseedでも本番では再現しない** — シード選抜には使えない。
ワークフロー: T1で構成を固める(≈1分/回) → 決まったら quality を外して本番(31分/回)。
