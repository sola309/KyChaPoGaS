# 音楽解析ロードマップ（2026-08-20）

音ハメ・リズム緩急を映像制作に使うための解析基盤。優先度はユーザー承認済み。

## 現状（実装済み）

| 機能 | 実装 | 精度(実測) |
|---|---|---|
| ビート/小節線 | `beat_this`(2024) | 誤差 ±0.4f 程度。本作のグリッドは確定済み |
| 楽曲構造 | **自作**(クロマ自己類似+エネルギー+ステム) | 境界誤差 0〜3.4秒 / 6箇所中3箇所は0秒 |
| 移動量バジェット | 自作(伴奏低域の持続→画面幅%) | — |
| 打撃 | HPSS+オンセット検出 | 拍一致 80%(低域差分方式は48%だった) |

自作構造検出器の既知の弱点:
- 「つなぎ」が残余カテゴリで、性格の違う区間(イントロ後半 / 間奏前半)が同居する
- プレサビが独立して取れない(メロに吸収される)

## 優先度1: All-In-One Music Structure Analyzer への置き換え

- https://github.com/mir-aidj/all-in-one / 論文 https://arxiv.org/abs/2307.16425 (ISMIR 2023)
- **MITライセンス**。`pip install allin1`
- 出力: BPM / beats / downbeats / 区間境界 + **機能ラベル**
  `intro / verse / chorus / bridge / inst / solo / break / outro`
  → 上記の弱点2つが**語彙レベルで解決する**(`break`=抜き, `inst`=間奏, `bridge`=プレサビ相当)
- 100FPSのフレーム単位アクティベーションも取得可 → 移動量バジェットの材料に直接使える
- Harmonix Set で4タスクすべてSOTA

### 導入検証の結果(2026-08-20)
- **NATTEN 0.21.7 のaarch64ビルド成功**(wheel 19.7MB)。失敗の原因は2つとも環境側だった:
  1. ビルドスクリプトが `python` を直接呼ぶが、この環境には `python3` しかない
     → `tools/music-struct/.shim/python` にシンボリックリンクを張ってPATHへ
  2. nvcc がPATHに無く、ninja が未導入
     → `export PATH=/usr/local/cuda/bin:...` + `CUDA_HOME=/usr/local/cuda`、`pip install ninja`
  再現する場合はこの2点を先に用意すること。
- madmom は GitHub 版必須(PyPI版はPython 3.12で壊れている)
- 本体の `backend/.venv` を汚さないため `tools/music-struct/.venv` に隔離

### 置き換え方針
既存の `audio_structure` と同じ JSON 形へ変換して差し込む。呼び出しは
ADTOF と同じく **subprocess のCLI越し**(依存衝突を避けるため本体からは直接importしない)。

ラベル対応:

| allin1 | 本作 | SECTION_GAIN | 備考 |
|---|---|---|---|
| `chorus` | サビ | 1.00 | |
| `inst` / `solo` | 間奏 | 0.95 | |
| `bridge` | **プレサビ** | 0.80 | 新設。サビへの助走なので中〜大 |
| `verse` | メロ | 0.65 | |
| `break` | **抜き** | 0.15 | 新設。ここで画を止めてサビ頭との落差を作る |
| `intro` | イントロ | 0.30 | |
| `outro` | アウトロ | 0.30 | |

→ 自作版の「つなぎ」(残余カテゴリ)は廃止。`break` と `inst` に分かれて解決する。

UI 側は `MotionBudgetLane.tsx` の `SECT_COLOR` に プレサビ/抜き を足すだけ。

### 自作版との比較で見るべき点
自作版の実測: 境界誤差 0〜3.4秒(6箇所中3箇所は0.0秒)、区間15。
allin1 で同じ6箇所を測り、**改善しなければ自作版を残す**(依存の重さに見合わないため)。

## 優先度2: ドラム個別打点（キック/スネア/ハイハット分離）

現状は HPSS で打楽器を1つにまとめており、**役割の違う当たりが混ざっている**。
「打撃が多すぎる」という指摘の本質はここにある可能性が高い。

- **ADTOF** — CRNN、5クラス(キック/スネア/ハイハット/タム/シンバル)
- 2025-09 の研究 https://arxiv.org/abs/2509.24853 — ドラムステム分離と組合せて7クラス+MIDIベロシティ
- Omnizart — 打楽器含む汎用採譜

### 映像への割り当て(設計案)
| 打点 | 映像の役割 |
|---|---|
| キック | 画面の押し(Push/寄せ)・被写体の踏み込み |
| スネア | **カット**・反転・ワイプ |
| ハイハット/シンバル | フラッシュ・粒子・細かい震え |

## 優先度3: テンポグラム（リズムの質感）

- AudioLabs Tempogram Toolbox https://www.audiolabs-erlangen.de/resources/MIR/tempogramtoolbox/
- novelty curve の局所周期性 →「いま何分音符で刻まれているか」
- 用途: **カットの刻み密度を実際の刻みに合わせる**。間奏後半の転調(150.0s)で
  刻みが変わっているなら映像も変える

## 優先度4: 緊張度（テンション）の時系列

- TenseMusic (PLOS ONE, オープンソース)
  https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0296385
- 音声のみから musical tension を時系列予測。映画音楽データセットで学習
- 移動量とは**別の軸**: 同じ移動量でも、張り詰め→固定+細かい震え / 緩み→ゆったりトラック
- 本作のテーマ(引き裂き)と相性が良い

## 参考: 評価指標の流用

映像↔音楽生成の分野で使われる **BCS**(beats coverage score) / **BHS**(beats hit score) は、
「カットが拍に乗っているか」の全尺採点にそのまま使える。
現状は目視と個別の誤差フレーム数で見ているが、1つの数字にできる。

## 採用しないもの

音楽→映像生成(ChoreoMuse, MoMu-Diffusion)、映像→音楽生成(VMAs 等)は活発だが、
本作は **H3で生成した映像を人が編集する** 方式なので直接は使わない。
